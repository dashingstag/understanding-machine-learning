KV cache vs context length

The bottleneck is bytes, not FLOPs

Did you know?

Decoding one token rereads every weight — a 7B fp16 model is a 14GB memory read per token. Modern GPUs have FLOPs to spare; the wire is what you pay for.

In the real world

Every $/token price you see is memory bandwidth + scheduling. Reasoning models turned 100-token answers into 10k-token answers — efficiency is now the margin.

Prefill is compute-bound (all tokens at once); decode is bandwidth-bound (one token at a time). The entire efficiency toolkit is ways to read fewer bytes per token.

The KV cache — the other memory hog

Did you know?

KV caching skips recomputing past keys/values — but the cache grows linearly with context: 128k tokens ≈ tens of GB on a big model. GQA and MLA exist purely to shrink it.

Every past token's K/V stays resident so attention can look back. Cache per token: $2 \cdot L \cdot n_{kv} \cdot d_h \cdot \text{bytes}$ — the panel grows it linearly with context.

Four levers, one goal: fewer bytes

Did you know?

Speculative decoding is provably lossless — a draft model proposes, the big model verifies $k$ tokens per pass and rejects any mismatch. Same distribution, 2–3× faster.

In the real world

4-bit quantization halves decode time again on top of that — distillation changes the model entirely; batching (vLLM) sets fleet throughput. Production serving stacks use all four.

Quantization shrinks weight bytes; speculation amortizes them; distillation shrinks the model; paged attention shrinks the cache's fragmentation. None changes the math of attention — all change its bill.

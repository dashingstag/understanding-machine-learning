Three axes of splitting

The constraint is memory, not FLOPs

Did you know?

A 70B model needs >1TB of optimizer state under Adam — the optimizer costs more bytes than the weights. Nothing about this problem is the math; it's the bytes.

In the real world

The field's unit of progress is MFU — what fraction of peak FLOPs you actually get. 40–50% is good; every point is real money at 10⁴-GPU scale.

Pretraining arithmetic — 6ND FLOPs — fits on no single device. The run exists because three orthogonal splits, composed, make it fit: batch, matrix, layer.

Axis 1 — split the batch

Did you know?

ZeRO-3 / FSDP shard everything — weights, gradients, optimizer state — across the replicas; each GPU materializes a layer just-in-time via all-gather. That's how 1TB of state fits on 80GB cards.

Data parallelism: every GPU holds the model, gets a slice of the batch, and the gradients are all-reduced each step. The default strategy — everything else exists only for what doesn't fit this way.

Axes 2–3 — split the model

In the real world

Tensor parallelism needs an all-reduce per block — it lives inside the NVLink island only. Pipeline parallelism crosses nodes but leaves stages idle — the "bubble" that microbatch scheduling fights.

Tensor parallelism shards each matrix across GPUs — intra-layer, bandwidth-hungry. Pipeline parallelism hands layer ranges to different device groups — an assembly line with warm-up/cool-down waste. A 3-D recipe (TP inside node, PP across nodes, DP across replicas) trains the trillion-parameter class.
